# Spelling & Grammar Check

Catches typos in everything unparty.app publishes, without slowing you down.

Built for the way this repo actually gets written: fast, in one pass, at midnight,
by someone who would rather ship than proofread. So the rule is simple — **this
check reports, it never blocks.** No red X on your PR because you wrote "teh".

## The 30-second version

```bash
npm run spellcheck        # what did I break in the prose I just wrote?
npm run spellcheck:fix    # fix the mechanical stuff automatically
./spellcheck add unppp    # "that's a word, actually"
```

Install the git hook once and you'll see it on every push:

```bash
npm run frontmatter:install-hooks
```

That's it. Everything below is detail you can read when you need it.

## What it catches

Two passes over the same files, reported separately.

### `SPELLING.` — real words vs. not-words

[cspell](https://cspell.org) with an English dictionary plus software, TypeScript,
HTML, CSS, npm, fonts and filetype dictionaries, tuned so this repo's vocabulary
is invisible to it.

```
  SPELLING.
    public/covers/stories/story-025.md
      41:12      entrpreneurs             → entrepreneurs, entrepreneur, entrepreneur's
      52:3       meticuliosly             → meticulously, meticulosity
      63:18      wtih                     → with, twig, twin
```

It suggests the correct spelling, which is the part you cannot hand-roll without
a dictionary — and the reason this brings in a dependency at all.

### `GRAMMAR.` — four mechanical rules

`scripts/grammar-check.js`. No dependencies, no network, no model. Four rules,
chosen because each one is *decidable from the text alone*, so it can be trusted
to auto-fix:

| Rule | Catches | Auto-fix |
| --- | --- | --- |
| `doubled-word` | `the the`, `about about` | ✅ |
| `missing-apostrophe` | `dont`, `youre`, `wasnt`, `Thats` | ✅ |
| `article-agreement` | `a idea`, `an founder` | ✅ |
| `space-before-punctuation` | `ready ; it was`, `point .` | ✅ |

Anything marked `✎` in the output is fixable by `npm run spellcheck:fix`.

Two contractions are reported but **never** rewritten: `cant` and `wont`. Both
are real English words (`a cant phrase`, `wont to wander`), so silently rewriting
them could change your meaning. You get told; you decide.

## What it deliberately doesn't catch

This is the important part, and it comes straight from the real data in
[#553](https://github.com/unparty-app/theunpartyapp/issues/553).

When 35 book titles were fixed, the typos fell into three classes:

**1. Non-words — caught.** `MOONWALKING WITH WINSTEIN` → Einstein,
`CUSTOMER EXXPERIENCE 3.0` → Experience, `POVERY, BY AMERICA` → Poverty. A
dictionary handles all of these. ✅

**2. Missing possessive apostrophes in titles — not caught.** `A HACKERS MIND`
should be `A Hacker's Mind`, but "hackers" is a perfectly good plural. Deciding
between them needs the meaning of the sentence. Flagging every bare plural would
bury you. ❌ by design.

**3. Real-but-wrong names — not caught.** `Steve King` should be `Steve Krug`.
Both words are correctly spelled, common names. No spell-checker on earth catches
this. ❌ by design — it needs a second pair of eyes at data-entry time, not a
linter.

Also out of scope, for the same reason: `its` vs `it's`, `their`/`there`/`they're`,
and comma splices. Each needs sentence meaning, and each would generate more
false alarms than catches. **A checker that cries wolf is a checker you turn off.**

### Freeform database content

Per the discussion in #553 about spot-checking database text fields: this already
works, with no extra machinery. Two generated markdown files carry live DB content
into the checker's scope:

- `docs/reports/what-does-unparty-store.md` — regenerated by `npm run db:snapshot`
- `src/app/admin/books/books.md` — the `Book.title` / `Book.author` reference

Because those are markdown, they get spellchecked like anything else. Running
`./spellcheck --all` against them today surfaces two author typos that survived
the last cleanup:

- `Ali Amminian` → **Aminian** (`Machine Learning System Design Interview`)
- `Cremas` → **Cremades** (`The Art of Startup Fundraising`)

Fix those at the source via `/admin/books`, then regenerate the file — don't edit
the generated markdown, it'll just come back.

## Where it runs

Three places, same checker, same output.

### 1. Your terminal

```bash
npm run spellcheck
```

Checks only the prose you've changed against `origin/main`. On a normal branch
that's a handful of files and about two seconds.

### 2. Your git hook (on push)

```bash
npm run frontmatter:install-hooks   # one time
```

Installs `pre-push`, which checks the commits you're about to push and prints
what it finds. **It always lets the push through.** To skip it entirely:
`git push --no-verify`.

### 3. Your pull request

`.github/workflows/spellcheck.yml` runs on every PR into `main` and:

- writes the report to the job summary,
- keeps **one** PR comment up to date (it edits, it doesn't pile up),
- says nothing at all when the prose is clean,
- and **always passes**, so it can never block a merge.

## Command reference

```
./spellcheck [options] [files...]
./spellcheck add <word>...
```

| Option | What it does |
| --- | --- |
| *(none)* | Check prose changed against `origin/main` |
| `--all` | Check every tracked prose file |
| `--staged` | Check what's staged for commit |
| `--base <ref>` | Compare against `<ref>` instead of `origin/main` |
| `--fix` | Apply the safe grammar fixes, then report what's left |
| `--no-color` | Plain output (also honours `NO_COLOR`) |
| `-h`, `--help` | Show usage |

| npm script | Equivalent |
| --- | --- |
| `npm run spellcheck` | `./spellcheck` |
| `npm run spellcheck:all` | `./spellcheck --all` |
| `npm run spellcheck:fix` | `./spellcheck --fix` |

**Exit codes:** `0` clean · `1` issues found · `2` bad usage or cspell not installed.

**Scope:** `.md`, `.mdx`, `.txt`, and `content/articles/*.json`. Prose that ships
to readers — not code comments or UI strings, which are far noisier and much less
likely to be read by anyone.

## Teaching it new words

Every project has words the dictionary doesn't. When the checker flags something
that's spelled right:

```bash
./spellcheck add unpartyverse
git add .cspell-words.txt && git commit -m "spellcheck: unpartyverse is a word"
```

The word goes into `.cspell-words.txt`, which is plain text, one word per line,
grouped under comments. Edit it by hand if you prefer.

**You don't need to add** anything starting with `unparty`, `theunparty` or
`unppp` — those are matched by pattern in `cspell.json`, including inside
identifiers like `isUnpartyMember` and `user_unppp_visits`. A typo in the *rest*
of the word still shows up, which is the point.

### One rule about adding words

**Add them one at a time, after you've checked.** Do not bulk-add every name the
checker flags to make the output green.

If someone had bulk-added the book author list when this was built,
`Ali Amminian` and `Cremas` would be in the dictionary right now and nobody would
ever find them again. A noisy backlog is recoverable. A dictionary full of typos
is not.

## Getting Claude to fix things

`claude.yml` responds to `@claude` mentions on issues and PRs. If the report is
long and you'd rather not work through it:

> `@claude fix the spelling and grammar issues on this branch`

Good things to delegate: a long list of genuine typos in a draft; deciding which
flagged names are real and adding them to `.cspell-words.txt`; the judgement-call
classes this checker deliberately skips (`its`/`it's`, possessive titles).

Things to do yourself: anything in a quote, a transcript, or someone's name.
Automated "corrections" to those are how `Steve Krug` became `Steve King`.

## How it stays quiet

The checker only earns its keep if you leave it switched on, so:

- **Changed files only.** The default never shows you a backlog you didn't create.
- **No `paths:` filter on the workflow.** A skipped check can leave a PR pending
  forever; this one always runs and exits in seconds when no prose changed.
- **One PR comment, edited in place.** Not one per push.
- **Silence when clean.** No "✅ 0 issues" comment on every PR.
- **Never a failing check, never a blocked push.**
- **Duplicates suppressed.** cspell flags `dont` too, but grammar-check already
  reports it with the actual answer, so only one of them speaks up.

### The existing backlog

`./spellcheck --all` currently reports a few hundred issues, over half of them in
one file: `src/app/theunpartycrawler/claude_report.md`, a verbatim LLM chat
transcript. That's expected and fine. Nobody has to clear it — the default mode
never shows it to you, and "fixing" someone else's transcript would falsify it.

## Troubleshooting

**`cspell is not installed. Run: npm install`**
The checker uses the pinned local copy at `node_modules/.bin/cspell`, never a
downloaded one. Run `npm install`.

**`origin/main not available — checking uncommitted changes instead`**
A shallow clone (CI sometimes, or `git clone --depth 1`). The checker falls back
to your working-tree changes rather than checking nothing. Run
`git fetch origin main` for the real comparison.

**It flagged a word inside a code block.**
It shouldn't — fenced blocks, inline code, link targets, HTML tags and long
opaque IDs are all masked before checking. If one slips through, that's a bug in
the patterns in `cspell.json`.

**Too much noise in one file.**
Add it to `ignorePaths` in `cspell.json` if it's generated or verbatim. Think
twice first: noise usually means the file has real problems.

**`--fix` changed something it shouldn't have.**
It's `git diff`-able and reversible, and it never touches code blocks, inline
code or link targets. If it got something wrong, please open an issue with the
line — that's a rule that needs tightening.

## Design notes

For anyone extending this later.

**Why cspell and not a grammar service?** The issue asked what the options were.
A hosted grammar API (LanguageTool, Grammarly) means sending unpublished drafts
to a third party, an API key in CI, and rate limits on every push. A local
dictionary plus a short list of mechanical rules covers the errors that actually
appear in this repo, runs offline in seconds, and has no per-check cost.

**Why cspell 9.6.0 exactly?** It was the newest release that ran on Node
20.17.0, which the repo used when the pin was set (cspell 9.6.1+ needs Node
≥ 20.18, and cspell 10 needs ≥ 22.18). The repo is now on Node 24 (`.nvmrc`,
every workflow), so that limit is gone, and moving to cspell 10 is a separate
upgrade. The version stays pinned exactly, because a floating range would let
a new release change the results in CI without anyone touching the repo.

**Why is the grammar half hand-written?** Because the four rules are the whole
job. Each is decidable from the text alone, which is what makes auto-fix safe.
Adding a rule that needs sentence meaning would mean it can no longer auto-fix,
and a grammar checker you can't trust to fix is just a nag.

**Why mask with `\0` and not spaces?** Blanking inline code to spaces invented
167 phantom "stray space before comma" errors — `` `a`, `b` `` became `   ,   `.
NUL is neither a word character nor whitespace, so masked regions vanish from
every rule while keeping byte offsets aligned for `--fix`.

**Why does it report instead of failing?** Because the alternative was tested by
everyone who has ever added a linter to a writing workflow: people stop writing
in the repo. The check that runs is worth more than the check that's strict.

### Files

| File | Purpose |
| --- | --- |
| `spellcheck` | The CLI. Orchestrates both passes and renders the report |
| `cspell.json` | Dictionaries, ignore paths, and the jargon-masking patterns |
| `.cspell-words.txt` | Project vocabulary. Safe to edit by hand |
| `scripts/grammar-check.js` | The four grammar rules and `--fix` |
| `scripts/pre-push-spellcheck` | The git hook (installed, not run from here) |
| `.github/workflows/spellcheck.yml` | The PR check and its sticky comment |
